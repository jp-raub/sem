# 手動通知：原子的な送信受付基盤

英語正本：`MANUAL-NOTIFICATION-ACCEPTANCE.md`。

## 今回の範囲

読取専用プレビューの後続として、Coreの明示受付メソッド、2テーブル、追加EF Core移行、合成SQLite試験を追加する。HTTP経路・作成画面・自動呼出し・Push配信ワーカー・SMTP経路・新配布・DXP更新は追加しない。今回の対象者別Push送信待ちは、まだどのワーカーも消費しない。「受付済み」はメッセージと永続意図の保存完了であり、端末受信／既読ではない。

## 操作IDと現在の認可

`AcceptEventManualNotificationAsync` は小文字D形式GUID、明示確認、正規化した平文下書き、プレビュー比較値を要求する。トランザクション内で現在のアカウント／セッション／SecurityStamp、DB上の全体／担当イベント管理者を独立に再確認し、比較値を認可に流用しない。

未受付なら、現在の演奏／観覧登録者・有効／メール確認済み・イベントの実効閲覧条件でプレビューを再計算する。本人・イベント版／タイトル・内容・対象者が変わった場合は新しいプレビューが必要。対象0人は受付不可。検証と保存を同じSQLiteトランザクションに置く。

受付済み操作IDは本人・イベント・正規化要求ハッシュに固定し、同じ操作ID／要求の再試行は元の人数／時刻を返すだけで追加保存しない。別の内容／比較値／本人／イベントでは再利用できない。結果の再取得でも現在の管理権限とセッションが必要。後から参加登録が変わっても受付済み履歴へ追加／変更しない。新しい操作IDは意図的な別送信として扱い、同一本文だけを全体で重複排除するものではない。

## 一括保存

次の4つを一括コミットする。

1. `ManualNotificationOperations`：本人／イベント、要求ハッシュ、プレビュー根拠、受付時刻／人数、受付済み件名／本文。
2. 人物ごとに1件の通常の未読 `Messages`。IDは操作／イベント／本人から決定的に生成。
3. `ManualNotificationRecipients`：イベントに紐づく対象スナップショット、同じメッセージID、未稼働の `PushState=Pending`。操作×人物の一意制約と外部キーを設定し、購読秘密情報は保持しない。
4. 操作IDを参照する `ManualNotificationAccepted` 監査。診断文に本文や秘密の宛先情報を記録しない。

途中失敗は全件取り消し。コミット後に応答を失った場合は同じ操作ID／要求で結果を回復する。返却に宛先一覧を含めず、旧通知ヘルパー・SMTP・既存自動Push・予定台帳を呼ばない。既存Identity／鍵ストア・メッセージ・予約配信・サービス設定は書き換えない。

追加移行 `AddManualNotificationAcceptance` は2テーブルと索引の作成だけ。Downは新テーブルだけを削除するが、運用受付後の安易な巻戻し手順ではない。旧アプリ／DBへ戻す場合は別途データ保持計画が必要。DXPで移行を実行する変更ではない。

## 検証

専用コンソール試験で入力／明示確認／現認可、古いプレビュー拒否、監査保存失敗の全件ロールバック、再試行／操作ID誤用、同時3要求、実際の別プロセスによるDB再オープン／再取得、データ入り旧スキーマからの追加移行、既存アカウントstamp／既読メッセージ／予約ペイロード／設定の保持、無関係な業務操作の非変更、EF差分なし、SQLite整合性／外部キーを確認する。別プロセス試験をWebコンテナ再起動や実ブラウザ試験とは扱わない。

実行は `dotnet run --project tests/Sem.ManualNotificationAcceptanceChecks -c Release`。専用workflowではRelease警告エラー化ビルドと、専用試験＋既存全.NETコンソール回帰を実行する。ローカル結果とCI結論はPR／ダッシュボードに記録し、本書の存在だけで合格とはしない。
