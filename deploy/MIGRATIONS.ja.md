# SQLiteマイグレーション基盤

英語正本は [MIGRATIONS.md](MIGRATIONS.md)。

この候補版の変更対象は**DB起動・更新基盤**です。正式な業務モデルや認証方針の変更ではなく、DXPを自動更新するものでもありません。反映前に開発PRと同じコミットのCI結果を確認してください。

## 対応するDB状態

- 空のSQLite DBはEF Coreの `20261012082319_ExternalTestBaseline` から作成します。
- 固定配布版 `78b9a6c` がEnsureCreatedで作成した外部テストDBは、**全スキーマが基準と一致する場合だけ**取り込みます。SQLiteのDDLでテーブル・列・インデックス・制約・ビュー・トリガーを照合します。書式上の空白は正規化しますが、意味が同じでも手書きDDLの違いを保守的に拒否する場合があります。
- 既に基準移行済みのDBは、履歴がアプリの既知マイグレーションの先頭から連続したものか、履歴に対応するスキーマと一致するかを確認した後に未適用分を適用します。

元の `00000000000000_CreateIdentitySchema` は配布版で使われていなかったテンプレートです。追跡用にファイルは残し、設計時の検出属性を無効化しました。この古いIDが登録されているDBを無条件に現行履歴へ付け替えず、個別確認のため停止します。

## 取り込みと失敗時の動作

1. SQLite以外のプロバイダー、マイグレーションがないモデル変更を拒否します。
2. SQLiteの即時トランザクション内で履歴とスキーマを読み、同梱マイグレーションから作成した参照DBと比較します。
3. integrity_checkがok、foreign_key_checkが違反0件であることを確認します。
4. 一致する旧DBだけに履歴テーブルと基準履歴を原子的に登録します。業務テーブルの再作成、ユーザー・パスキー・招待・通知データの書き換えは行いません。
5. 取り込みを確定し、通常の更新はMigrateAsyncで適用します。EFのSQLite移行ロックも管理用スキーマとして照合し、自動削除はしません。

未知の履歴、欠けたスキーマ、余分なテーブル／ビュー／トリガー、欠落・変更されたインデックス、整合性違反は、推測して修復せず起動を停止します。EnsureCreatedへの戻し、DB削除・作り直し、履歴の手動追加、検証無効化で通そうとしないでください。バックアップを保全して調査します。外部テスト版は複数アプリの同時稼働を想定しません。更新前に旧インスタンスを停止します。

基準移行は**現在の簡易テストモデル**を維持します。PostgreSQL、正式なイベント／曲／タイムテーブル、追加制約、パスキー追加の強化は別作業です。初回登録・ログインの動作は変更しません。

## 候補版の検証

```sh
dotnet build src/Sem.Web -c Release
dotnet run --project tests/Sem.StorageChecks -c Release
```

合成ユーザー・パスキーのバイト列・招待・メッセージ／配信／端末・イベントで、空DB作成、旧DB取り込み、再起動、移行済みDBのコピー復元、拒否時のDBファイル無変更を確認します。旧配布版を再現するため、**テスト用DBの作成だけ**にEnsureCreatedを使用します。

独立した「SQLite migration foundation」CIでは固定旧版と候補版のlinux/amd64イメージをビルドします。HTTPS・CSRF・仮想パスキー・隔離SMTPの統合テスト後、同じ合成データボリュームを維持して旧版から候補版へ切り替え、保護鍵による既存セッション、招待、メッセージ、管理者／一般ユーザーの既存パスキー再ログイン、予約処理を検証します。このCIはソースへの書き戻しやPRマージをしません。実Apple端末・実SMTP／Pushの到達確認とは別です。

dotnet efはIdentityスキーマVersion3を設定した専用インメモリファクトリーを使い、アプリ起動や実DBへの接続を行いません。モデル変更時は新しいマイグレーションを追加し、適用済みの基準移行を書き換えないでください。

## 将来DXPへ反映する前の条件

- `/data` 全体（DB＋保護鍵）の**最新停止中バックアップ**、チェックサム、非公開.env、旧イメージを保持します。バックアップはBACKUP.mdの手順を使い、秘密情報を公開しません。
- イメージ／ソースの固定コミットを確認し、まず現ボリュームの別コピーで試します。今回の実装はユーザーのDXP実DBへ接続していません。
- 元ボリューム・公開ホスト名／RP ID・VAPID鍵・Data Protectionのアプリ識別を維持します。手元のSMTP認証IDと表示名付きSMTP_FROMも維持し、.envを設定例で上書きしません。
- コピー側のスキーマ／整合性・既存パスキー再ログイン・招待状態・通知テスト後に、単一インスタンスで切り替えます。
- 基準移行だけなら業務スキーマは同じで、元ボリュームを戻し先として残します。将来のスキーマ変更後は、旧バイナリに戻すだけで復旧できるとは考えず、切替後の変更も考慮して元ボリューム／バックアップから戻します。

本書は反映前の条件整理であり、**DXP更新を実行する許可・指示ではありません**。
