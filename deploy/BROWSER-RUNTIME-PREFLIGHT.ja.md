# 公開を止めたブラウザー準備遅延への限定対処

## 観測した障害

PR124を統合したmain `50445c6c2ae5b226c44c1de2a288951b18b0b413` の必須CI `40222489819` attempt1では、integration成功に対してacceptance-browserが30分で中断した。ブラウザー依存準備は18:42:25〜18:49:42の**7分17秒**、実アプリの検査はその後に開始し998件まで進んでいた。公開ゲートは非成功の候補を通さない。PRの両CI成功やローカルfull1004件成功を、この統合mainのfull成功に読み替えない。

依存準備ステップの公開時刻から遅延を確認したが、APTの特定ミラーや通信の原因まで確定したとはしない。CI改善を本筋とせず、この公開を妨げた重複準備に限定する。

## 変更

固定Playwright 1.56.1と同じheadless Chromiumを従来どおり取得し、製品・DB・ネットワーク先を使わない空ページで実起動を検査する。

- 起動してページを扱えた場合だけOS依存の再導入を省く。製品の受入検査自体は省かない。
- 起動エラーに共有ライブラリ不足の明確な診断がある場合だけ、公式の `playwright install-deps chromium` を実行し、同じ起動検査をもう一度必須実行する。
- タイムアウト、実行ファイル欠落、権限、sandbox、その他の失敗はOS依存と推測せず、そのまま非成功にする。
- ブラウザーは成功／失敗とも閉じ、後始末の失敗も無視しない。外部へ生の起動ログや環境情報を出さず固定分類だけを表示する。

両jobで同じ条件を使う。40分／30分枠、固定バージョン、キャッシュの対象、fullと独立UI fixture、全assertion、全データ一式バックアップ・復元・Docker検証、CD成功条件は変更しない。起動プローブに成功しても全ライブラリ・全画面の成功を保証するとはしない。必須CIが引き続き検出する。

## 評価

合成検査で成功／共有ライブラリ不足／それ以外の失敗／後始末とworkflowの両接続を確認する。ローカルでは同じ固定ブラウザーで実起動を確認する。速度改善や恒常値は新規CIの時間を観測してから判断し、単一成功を中央値と呼ばない。
