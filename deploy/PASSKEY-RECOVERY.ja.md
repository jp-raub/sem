# 管理者承認によるパスキー復旧

この機能は、通常のパスワード再設定やメールだけでのログインではなく、例外的なアカウント復旧手段です。サービス全体の管理者が対象アカウントを選び、監査理由を入力し、取り消せないリセットを明示確認したうえで、自身の登録済みパスキーを使って再認証します。イベント限定管理者には実行権限がありません。

## フローとセキュリティ

1. 管理者は `/service/passkey-recovery` から復旧を開始します。APIは、サービス全体の管理者ロール、アカウントの有効化・メール確認状態、セキュリティスタンプ、認証セッションの失効状態を毎回データベースで再確認します。
2. ASP.NET Core Identityのネイティブなパスキー assertion は、対象・理由・管理者セッションに紐付けられます。成功したassertionの消費、対象の無効化、セキュリティスタンプの更新、既存パスキー全件の削除、保留中のパスキー追加・メール変更フローの失効、Push端末との紐付け削除、監査記録、保護メールのキュー登録は、同一トランザクションで行います。
3. 復旧メールは、アカウントに保存済みの確認済みアドレスだけに送信します。リンクは `/recovery#op=…&token=…` 形式で、秘密トークンはURLのフラグメントに置き、クエリ文字列には含めません。トークン本体は操作レコードにはハッシュのみを保存し、データ保護されたメールキューに限り暗号化して保持します。復旧リンクのoutbox行には、キュー済みメールが現在有効な操作tokenと一致することを照合する別個のSHA-256 `ProofHash` も保持します。送信成功後は保護本文を消去しますが、このdigestは残ります。これはbearer tokenではありませんが秘密情報として扱い、ログや監査記録には出力しません。
4. 匿名のメール確認はトークンを一度だけ消費し、対象と復旧用途に限定した短時間の登録grantを返します。アプリのCookieや通常の認証セッションは発行しません。
5. grantで許可されるのは、Identityネイティブなパスキー作成・attestationだけです。新しいパスキーの保存が成功するまで対象アカウントは無効のままです。完了時にgrantと復旧状態を消去し、セキュリティスタンプを更新してアカウントを再有効化し、保護された完了通知をキューに登録します。利用再開には新しいパスキーで通常ログインが必要です。

元のメールアドレス、内部ユーザーID、ロール、業務データは維持します。別のメールアドレスを復旧フローで指定することはできません。削除されたパスキーを公開APIから復元することもできません。

## 期限と永続レート制限

- 初回の復旧メールと操作は、リセット開始から15分で期限切れになります。再送には管理者パスキーによる新しい再認証が必要です。再送でトークンはローテーションされ、古いリンク/grantは無効になり、期限は延長されません。
- メール確認後のgrantは最長5分で失効し、対象アカウント、保存済みメール、セキュリティスタンプ、操作、復旧用途に束縛されます。
- 復旧メールの受け付けはアカウント・用途ごとにローリング1時間あたり3回、かつ各送信間60秒以上に制限されます。メール配信側の再試行は新たな送信受け付けとして数えません。
- 管理者proof失敗と無効なメールproofは、アカウント・用途ごとにローリング15分で5回までです。保留中の操作でメールproofが5回目に失敗すると、操作を期限切れにし、期限を失敗時刻まで短縮し、token/grant/challengeのhashを消去して、未送信の保護済み復旧メールをキャンセルします。アカウントは無効のままです。メール失敗の永続ウィンドウが有効な間は、管理者proof options・復旧開始・再送を拒否します。ウィンドウ経過後の再開にも新しい管理者proofと同じ保存済みメールが必要です。レート状態は期限切れや復旧操作の再作成で初期化されません。
- 復旧処理以外の理由で無効化されたアカウントは、この手順では復旧できません。復旧操作が期限切れになってもアカウントは無効のままです。保存済み記録により復旧処理が無効化したことを確認できる場合に限り、新たな管理者承認で再開できます。

## 配備前提

- HTTPSで公開し、公開OriginとIdentityのパスキー/RP設定を配備先に合わせて設定します。メールリンクは設定済みの公開Originから作成します。
- この機能を利用する前にSMTPを設定します。専用の永続・データ保護済みoutboxが上限付き再試行を行います。操作・トークン・スタンプ・アカウント状態が無効になった復旧リンクは送信を抑止します。
- ASP.NET Core Data Protectionの鍵リングとデータベースを永続ストレージに保存し、バックアップします。対応するData Protection鍵がない状態でDBだけを復元すると、保護済みメールの読み出しに失敗する可能性があります。
- 対応するアプリケーションmigrationを配備します。SQLite起動時の初期化は、対応済みスキーマ/履歴を検査してから未適用migrationを実行します。未知のスキーマや履歴を安全に推測して取り込むことはせず、停止します。
- 受入テストでは実アカウント、本番SMTP、本番DBを使用しません。合成ユーザーとテスト専用メールtransportを使用してください。

## 検証と運用者受入

隔離されたチェックは次のコマンドで実行します。

```bash
dotnet run --project tests/Sem.PasskeyRecoveryChecks/Sem.PasskeyRecoveryChecks.csproj
```

チェックは使い捨ての合成SQLite DB、fakeパスキーadapter、fakeメールtransportを使用します。サービスDBや実SMTPに接続してはいけません。テストハーネスがテスト前の空DBバックアップを `/data/evidence/` に作成したことを確認してください。

配備先でルートを有効化する前に、次を確認します。

- 承認済みmigration適用後にアプリがストレージ準備完了を報告する。
- 配備環境のSMTP送信とData Protection鍵の永続化が機能する。
- 管理者はサービスUIにアクセスでき、イベント限定管理者はアクセスできない。
- 確認用フラグメントtokenはPOST本文経由でのみ処理され、クエリ文字列やログへ出力されない。
- 復旧完了後、新しいパスキーで再ログインする必要があることが画面に表示される。
- 開始・再送・メール確認・完了の監査記録に操作者、対象、理由、日時が含まれ、token、credential、challenge、session秘密値を含まない。

実アカウントのリセット、本番有効化、実メール送信、ホスト管理アクセスによる緊急復旧手順の変更は、本実装および受入チェックリストの対象外です。
