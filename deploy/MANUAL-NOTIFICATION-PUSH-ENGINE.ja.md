# 手動Pushの上限付き処理と任意登録ワーカー定義

## 境界

上限付き `RunOnceAsync`、期限／占有切れ整理、将来の明示構成用BackgroundService定義を追加します。**本番DI／HTTP／HostedServiceには登録しません。** 起動時の有効化・DB移行・HTTP制御・配布・実基盤受入は追加せず、既定OFFと有効化前受付への非後付けを維持します。

## 1回の処理

1. 送信鍵なしでも、期限切れPending・占有期限切れClaimedを最大20件整理。PendingはExpired、Claimedは停止前送信の可能性を残してUnknown。Unknownは自動再送で選びません。
2. 現在ONの場合だけ、元の受付印が現在世代で、受付以後／期限前、準備未記録の確定宛先を元の受付・宛先ID順に最大20件選択。`PrepareAsync` は別の直列化トランザクションで全条件を再確認し、走査結果を認可とはしません。無効／旧世代／期限切れ／印なしを後付け配信しません。
3. 期日到来・期限前のPendingを最大20件処理。配信部品が独立して占有し、I/O直前に現在権限／参加／紐付け／所有者／リース／期限を再確認。処理件数は呼出し数で、配信基盤受付や端末受信数ではありません。

準備対象の一時的なキーセット位置は、先頭20件がすべて失敗しても選択済み対象の先へ進み、末尾で先頭へ循環します。OFF／世代変更では位置を破棄し、ワーカーは各Scopeの破棄をまたいで位置を保持します。これは認可・対象所有権・永続チェックポイントではありません。再起動時には同じ対象を再走査し得ますが、永続準備・終端／トークン状態で同時実行の安全性を維持します。1件の故障はFailedItemsへ数え、独立した他の処理を続行。取消は伝播します。送信未設定では試行数を増やさず、期限整理は進みます。記録済みの端末なし／抑止は後から有効端末／参加が戻っても復活させません。

ワーカー定義は3秒ごとにScopeを作り、失敗件数／例外型だけを記録して取消で終了します。AddHostedServiceへ登録しておらず、アプリでは未稼働です。専用試験で明示的に偽送信へ構成して動作・停止を確認しますが、本番登録／運用有効化ではありません。

## 検証

`dotnet run --project tests/Sem.ManualNotificationPushEngineChecks -c Release` は合成SQLiteで32項目を検証します。既定OFF／非後付け、25宛先の20件上限と続き、空処理の非重複、未設定時の準備／試行0、20＋5件期限整理、遅延期限除外、端末なし非復活、1宛先故障の分離／回復、先頭20件の継続故障と後続5件の別Scopeでの進行・循環回復、停止リースのUnknown、現在参加拒否／再参加非復活、重複する全体走査の一回I/O、実ワーカーの試験構成／停止、取消、ボックス保持、自動／旧キュー分離、モデル一致／整合性／外部キーを含みます。

全39.NET回帰・固定ソースCI・隔離仮想パスキー／実Blazor互換性受入は、実配信基盤／実機とは別証拠です。既存Service Worker／ボックス本人認証は維持しますが、実機での新規保証ではありません。

## 残る統合

サービスの明示登録と運用の有効化画面／HTTP（現在Cookie本人一致、独立した全体管理者認可、Origin／CSRF／no-store、期待世代の明示確認、結果不明操作IDの回復）が残ります。その後に別承認の配布／有効化と実機受信を受入します。PKCSパッケージ修正とは別にランタイム／イメージの安全確認も必要です。今回DXP／実データ／鍵／公開経路／新配布／PRマージは行いません。
