# 手動Pushの運用制御

全体管理者向け `/service/manual-push` をサービス管理から開きます。長寿命Blazor回線の本人情報を信用せず、ブラウザの現在Cookieで再認可。返却は本人ID・現在ON/OFF／世代・ワーカー接続と鍵設定の真偽だけで、メール／宛先／購読／鍵／本文を含みません。HTML／APIはno-store。Coreは現在の有効／確認済みアカウント・stamp・一意な有効セッション・DB全体管理フラグを再確認し、担当管理者や偽ロールだけでは操作できません。

GET `/api/core/manual-push-control` は読取専用。変更はPOST `/api/core/manual-push-control-change?actor=...` だけで、設定Origin・CSRF・現在Cookie本人一致と独立したCore認可を要求します。false／0の場合も4プロパティすべての明示を要求し、不明プロパティを拒否し、正規GUID・期待世代・明示確認が必要。最初の400／403／409だけを明確な拒否とし、運用APIの429／5xx／通信失敗／不正成功応答は不明のままです。配信基盤から受信したWebPush429とは別です。

変更準備は承認ではありません。最初のawait前に操作ID・変更先・期待世代を固定し、処理中／不明では別操作・破棄・内部遷移を拒否、外部離脱も警告します。戻る操作は既定リンク遷移を持たないボタンとし、静的SSRの拡張遷移へ任せず、明示ガードとNavigationManagerを通します。応答喪失後は同一ID／要求だけで確認し、後の拒否で以前の保存を否定しません。権限喪失は私的画面と過去の操作結果を隠して未確認IDを保持し、別の現在Cookie本人では再表示／再試行できません。ブラウザ保存・認証状態ファイル・自動送信再試行は使いません。

成功応答はID／変更先／結果世代を検証。古い再取得結果は操作当時として表示し、現在ON/OFFには代入せず、別の現在認可付き読取で取得します。古いONの再取得で新しいOFFを変更・上書き表示しません。初回の明確な拒否は現在状態の再取得と再承認が必要。明示再取得は未送信承認を無効化し、取得中はDOMとハンドラーの双方で準備／承認／送信を停止して古い取得と変更を競合させません。取消は下書きだけを破棄します。既存Coreの状態・監査・台帳の原子的保存を維持します。

現行ソースではProgramが `AddManualNotificationPushPipeline` を呼び、`ManualPushRuntime(true)` と手動ワーカーを登録します。登録状態・永続的な有効化・ホスト鍵設定・配信の健全性は別です。有効化の既定はOFFで、起動／移行ではONにしません。ただし、既存DBの保存済みONを登録処理が強制的にOFFへ戻すわけでもありません。[パイプライン構成](MANUAL-PUSH-COMPOSITION.ja.md)の送信条件と将来の適用時注意を参照してください。ワーカー登録や合成ON/OFF試験は、配信基盤の受付や端末受信の証明ではありません。この文書修正は実行コード・有効化・DB・鍵・配備を変更しません。

元の運用制御増分では、状態専用35、JS通信、隔離した仮想パスキー／実BlazorのHTTP／画面試験を記録しました。全40.NETという件数も当時の履歴であり、現在の累積CIの成功や件数を示すものではありません。固定ソースCIは別の証拠として扱い、現在の実行完了後だけ最終件数を報告します。

サービス／ワーカー登録は後続で実装済みです。[構成](MANUAL-PUSH-COMPOSITION.ja.md)と[状態UI](MANUAL-PUSH-STATUS-UI.ja.md)の範囲・証跡を別途参照してください。既定OFF・有効化前の非後付け・元の600秒期限・参加解除後のボックス保持／Push抑止を維持します。ソース登録を配備・配信基盤／実機の受入と同一視しません。ユーザーの現行指示では運用環境は存在せず、運用環境ができた際の受入は別に確認します。
