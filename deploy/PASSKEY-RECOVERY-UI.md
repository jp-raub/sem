# Passkey recovery UI

This change supplies browser UI only. The backend owns routing, authorization, challenge validation, state transitions, persistence, delivery, and revocation. UI checks are defense-in-depth and do not replace server enforcement.

## Administrator flow

The authenticated operator page is `/service/passkey-recovery`. It starts with its controls hidden and attaches browser listeners before fetching `GET /api/passkey-recovery-admin-context`. That response contains `{ "actorId": "..." }`. The explicit target lookup is `GET /api/passkey-recovery-admin-context?id=<targetUserId>`, returning `{ "actorId": "...", "target": { "id": "...", "displayName": "...", "maskedRecipient": "...", "enabled": true, "recovering": false, "operationId": "...", "expiresAt": "..." } }`; operation and expiry fields may be absent when there is no recovery operation. The UI requires actor and target IDs to be control-free and at most 128 characters. It rejects unmasked email-looking recipient values and only displays the server-provided masked recipient.

A new recovery start requires an explicitly entered target, a reason whose trimmed length is 3–500 characters (no control characters), and a visible confirmation that all existing passkeys and sessions will be invalidated and delivery will go only to the saved email address. The same fresh reason is required for a new start after expiry. It obtains options with `POST /api/passkey-recovery-admin-options?expectedActor=<actorId>` and body `{ "targetUserId": "...", "reason": "..." }`; the response is `{ "publicKey": <native request options> }`. The browser runs `navigator.credentials.get` and sends `POST /api/passkey-recovery-start?expectedActor=<actorId>` with `{ "targetUserId": "...", "reason": "...", "credential": <serialized assertion>, "explicitlyConfirmed": true }`.

An active operation can be resent only while its server-reported expiry is in the future and the target is disabled/recovering. Resend uses `POST /api/passkey-recovery-resend-options?expectedActor=<actorId>` with `{ "operationId": "..." }`, then native `navigator.credentials.get`, followed by `POST /api/passkey-recovery-resend?expectedActor=<actorId>` with `{ "operationId": "...", "credential": <serialized assertion> }`. A resend keeps the original recorded reason; the UI does not request or transmit a replacement. A disabled target with a proven expired operation may start a new recovery, subject to a fresh reason and confirmation. Successful start/resend is reported as queued, not as delivered.

The confirmation checkbox is cleared after a successful start or resend and when the active recovery expires. The new-start reason is cleared after successful operations and when the selected target changes; an expired restart therefore requires a new reason and a new checkbox action.

Every authenticated POST has exactly one `expectedActor` query parameter. Actor, selected target, reason (for starts), confirmation, and UI generation are snapshotted across the proof flow. Changes invalidate proof; target state and operation expiry are rechecked before each write. Starting and resending use native passkey assertion, never sign-in. No POST is automatically replayed. An uncertain POST locks further writes until a deliberate read-only refresh reconciles server state. `401`/`403` clears the actor context, and `Retry-After` is shown as wait guidance.

## Public recovery and new passkey

The anonymous page is `/recovery#op=<operationId>&token=<secret>`. It reads only the fragment and removes it with `history.replaceState` before any network request. Confirmation is `POST /api/passkey-recovery-confirm` with `{ "operationId": "...", "token": "..." }` (no query string), returning `{ "userId": "...", "grant": "...", "expiresAt": "..." }`. This does not create a normal authenticated session.

The user ID and grant remain in JavaScript memory only. The grant is cleared at the earlier of its server expiry or five minutes after receipt; the registration action is disabled on expiry or page/navigation cleanup. Registration requires an explicit button action: `POST /api/passkey-recovery-options` with `{ "userId": "...", "grant": "..." }` returns `{ "publicKey": <native creation options> }`; the browser invokes `navigator.credentials.create`, then posts `{ "userId": "...", "grant": "...", "credential": <serialized attestation> }` to `POST /api/passkey-recovery-complete`, expecting `{ "message": "..." }`. The UI issues no session and links to the normal login page `/` after success. It does not navigate to `/Account`.

## Transport and backend boundary

All POST requests first obtain CSRF data from `GET /api/csrf` and send `X-CSRF-TOKEN`. Requests use `credentials: same-origin`, `mode: same-origin`, `cache: no-store`, and `redirect: error`; the public POSTs contain no query string. Requests are bounded to 25 seconds; native credential prompts are bounded to at most five minutes. JSON responses are limited to 1 MiB, CSRF responses to 64 KiB, and UTF-8 decoding is fatal. UI output uses `textContent`; errors are not rendered as HTML. Secrets, grants, assertions, and tokens are not written to local/session storage or logs.

The backend must independently enforce cookie-based admin authorization, actor binding, CSRF and origin checks, strict request parsing, WebAuthn challenge/RP/origin/signature/attestation validation, operation eligibility and expiry, one-use token/grant semantics, saved-address-only delivery, atomicity, and revocation of existing keys and sessions. The UI neither creates nor weakens those guarantees.
