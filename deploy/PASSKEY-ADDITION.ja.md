# 本人確認付きパスキー追加

[英語版が正本](PASSKEY-ADDITION.md)。

SQLiteマイグレーション基盤に積み重ねた変更です。DXP更新の許可ではなく、認証復旧・メール変更・キー削除・全セッション失効は実装範囲外です。

## 操作と承認済みの期限

1. 既存パスキーでログインします。変更前に発行されたセッションは通常利用を維持しますが、キー追加前にログアウト→再ログインが必要です。
2. 「パスキーを追加」から、そのアカウントの既存キーで再認証します。ASP.NET Core Identityのネイティブ処理で検証し、認証器の更新状態を保存します。
3. 呼出元が指定した別アドレスではなく、アカウントに**保存済みのメール**へ新しい一回限りの確認リンクを送信待ちにします。操作を開始した同じログイン済みブラウザ／プロファイルで開きます。
4. メール再確認後、新しいキーを登録します。Identityがネイティブに検証・保存し、完了時にアプリ内通知とメールを送信待ちにします。

全体期限は**既存キー再認証成功から15分**。メールリンクも全体期限までです。メール再確認後の登録権限は**5分と全体期限の早い方まで**。期限と同時刻になれば失効します。超過時は再認証からやり直し、再送で全体期限を延ばしたり、失効した登録権限を復活させたりしません。

再送は旧メールトークン・メール証明・登録用チャレンジを失効させます。取消しとログアウトはそのセッションの未完了操作を失効させ、新規開始は同セッションの旧操作を取り消します。別ユーザー／セッション、保存済みメール・SecurityStampの変更、無効アカウント、初回登録用トークン、再利用、直接APIからの登録要求は拒否します。通常ログインや過去のEmailConfirmedだけでは追加できません。

## 実装の境界

- `20261012093941_AddPasskeyAdditionProof` で `PasskeyAdditions` を追加し、既存基準移行は変更しません。
- 操作・ユーザー・認証セッションのハッシュ・保存済みメール・SecurityStampを紐付けます。メールトークンとチャレンジの用途紐付けはハッシュで保存。既存通知サービスのメール本文はData Protectionで保護されます。DB・バックアップ・保護鍵を公開しないでください。
- 用途の照合はIdentityのチャレンジ・origin/RP・署名・attestation検証を**置き換えません**。独自の暗号検証は追加しません。
- メール証明消費と追加完了はSQLiteの即時トランザクションで保護し、同時要求でも成功は一度だけ。監査には操作IDを記録し、生トークン・チャレンジ・資格情報を記録しません。
- ブラウザはURLの証明パラメーターを除去してから、同一origin・ログイン・CSRF付きPOSTで確認します。HTML取得だけでは消費せず、未ログインのスキャナーも確認できません。確認URLを共有・記録しないでください。
- 既存のOrigin／CSRF確認と全体APIレート制限を維持します。アカウント別再送制限、キュー／履歴の保持・掃除、実機網羅、広範な悪用テストは後続課題です。完全なセキュリティ認証を意味しません。
- SMTP認証ID、SMTP_FROMのアドレス／表示名、公開ホスト名／RP ID、VAPID鍵、Data Protection識別子を変更しません。既存.envを設定例で上書きしません。

## 検証

```sh
dotnet build src/Sem.Web -c Release
dotnet run --project tests/Sem.StorageChecks -c Release
dotnet run --project tests/Sem.PasskeyProofChecks -c Release
```

`Passkey addition proof` CIで上記とlinux/amd64旧版／候補版イメージを検証します。固定旧版78b9a6cで合成アカウントを作成し、同じDB・保護鍵を保って更新、既存ログイン・招待・受信箱・予約処理を確認。続けてネイティブ再認証、隔離SMTPでの証明と再送、メール確認／attestationの同時消費、完了通知、取消し、新しい仮想キーだけでの再ログインを検証します。追加ケースは `SEM_PASSKEY_ADDITION_CHECKS=1` で有効化します。実アカウント・SMTP資格情報・端末の実キーは使いません。

テスト用時刻で期限ちょうどの境界、ユーザー／セッションの紐付け、アカウント状態変更、一回限り・取消しを検証します。Chromiumの仮想パスキーでSafari／iCloud／iPadOSや実SMTP／Push到達まで確認済みとはしません。

## 将来の配置と戻し方

[移行前チェック](MIGRATIONS.ja.md)に従い、停止中の/data全体を新しくバックアップし、元ボリュームと非公開.envを保持。まず別コピーで検証し、旧インスタンスを停止してから更新します。同じ公開先で二重稼働させません。今回の実装ではDXPを更新していません。

更新後は新しいテーブルと移行履歴を持ち、基準移行だけの旧バイナリは意図的に拒否します。**古いイメージへの差替えだけで戻さず**、移行履歴改変や新テーブル削除もしません。保持した更新前ボリューム／バックアップへ戻し、切替後の変更をどう扱うか確認します。公開ホスト名／RP IDと保護鍵を維持してください。
