# メンバープロフィール：現在の登録履歴

メンバーの基本プロフィールは引き続き同一オリジンの `/api/core/profile?id=...` から取得します。登録履歴は明示操作のみです。プロフィール表示時には自動取得せず、バックグラウンド更新や自動再試行も行いません。閲覧者が「登録履歴を取得」を押した場合に限り取得します。

## プライバシーと表示範囲

- 基本プロフィールと履歴の両方で、ブラウザーの現在の同一オリジン認証Cookieを使用します。対象ユーザーIDはプロフィールの対象を指定するだけで、閲覧者を指定・上書きする値ではありません。Coreはリクエストごとに現在の閲覧者セッション、対象者の有効性、閲覧者の現在のイベント権限を検証します。
- `GET /api/core/profile-registration-history?id=<targetUserId>` は、空でない `id` がちょうど1つ、長さ128文字以下、制御文字なしの場合に受け付けます。POSTはハンドラーで `405` を返し、処理対象のGET／POST応答には `Cache-Control: no-store` を設定します。その他の未対応メソッドはルーティング側で `405` となり、そのヘッダーはこのハンドラーの契約範囲外です。
- 履歴は現在の登録状態のスナップショットであり、監査ログではありません。Coreはまず現在の登録候補イベントから新しい順に最大100件を選び、その後に閲覧者の現在の権限で絞り込みます。そのため100件未満または0件になる場合があり、より古い閲覧可能イベントがあっても候補外となることがあります。全履歴・出席記録・削除済みログではありません。
- 応答は対象ID、現在のイベント名・日付、観覧状態、現在の曲・パート表示項目だけです。メール、回答、認証・セッション値、非表示イベント数、合計件数、カーソルは含めません。
- クライアントは基本プロフィール（正規化済みプロフィール画像と有効なプロフィール設問への回答を含む）を4 MiB、履歴を4 MiBまでに制限し、UTF-8を厳密に検証します。ストリーム読み込みを含め25秒で中断し、リダイレクト、形式不正、上限超過は失敗として扱います。取得に失敗した履歴を完全なスナップショットとして表示しません。
- `403` を受けた場合、プロフィールと履歴の両方を画面から消去します。その後、明示的な再取得操作で現在のCookieを使って再試行できます。プロフィール更新・対象ID変更時にも古い履歴を消し、遅れて返った応答が新しいプロフィールを更新しないようにします。

## ローカル検証

ブラウザー通信の合成チェックは `node scripts/profile-history-transport-checks.mjs`、ループバック限定HTTPチェックは `dotnet run --project tests/Sem.ProfileRegistrationHistoryHttpChecks/Sem.ProfileRegistrationHistoryHttpChecks.csproj` で実行します。HTTPチェックは一時SQLiteデータベース、合成Cookie、ループバックの一時ポートのみを使用し、本番や外部サービスには接続しません。

リリース前に、実際のBlazorブラウザーで390px表示、公開／非公開イベントの範囲、閲覧者Cookie変更後の403、対象ID変更と遅延応答、プロフィール・イベント・曲名のエスケープ、明示操作のみでの取得を独立して確認してください。

既存の同一オリジンHTTPエンドポイントと現在Cookieの本人確認は維持します。プロフィール・履歴の取得結果は上限付きJSストリーム（4 MiB／4 MiB、25秒）でBlazorへ転送し、全体のSignalR受信上限は変更しません。
