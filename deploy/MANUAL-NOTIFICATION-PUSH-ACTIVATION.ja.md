# 手動Pushの有効化管理（内部APIのみ）

## 境界

現在の全体管理者だけが利用できるCore読取／更新APIと、操作台帳の追加移行です。HTTP経路・画面・ワーカー・送信接続は登録せず、起動／移行でPushを有効にしません。実運用での有効化／配布は引き続き別承認です。合成試験内のDB直接更新はフィクスチャ専用で、運用手順ではありません。

`ReadManualPushActivationAsync` は1つの読取トランザクションで現在認証とDB上のIsAdminを確認し、Enabled／Epochだけを返します。状態なしはOFF・世代0で、行を作りません。イベント担当管理者や偽Adminロールでは利用できません。

## 明示確認と再試行可能な更新

`SetManualPushActivationAsync` は明示確認、小文字D形式GUIDの操作ID、期待世代を要求します。新規操作と再取得の両方で、現在の有効／メール確認済みアカウント・stamp・未失効の認証セッション・DB上の全体管理者を確認します。

- SQLiteの非遅延トランザクションで元の通知受付と直列化し、時刻比較で順序を推定しません。
- ON／OFFの実変更ごとに世代を増加。無効化と再有効化も対象。同じ状態の確認は世代を回さず、通知期限を延長しません。
- 別要求の古い期待世代は競合。同じ操作の再試行は元の結果を返すだけで再実行しません。過去結果は現在状態とは限らず、OFF後に古いON操作を再試行してもONになりません。
- 別の本人／判断／期待世代に操作IDを流用できません。新しい確認操作は無変更も含め監査1件、再取得は追加なし。状態・操作・監査は原子的に保存し、故障時は全体ロールバック。世代上限は拒否します。
- 既存の受付印／ボックス／宛先状態／キューを後付け・書換え・消費しません。OFFは直ちに方針チェックを拒否し、再ONの別世代は古い受付を復活させません。元の通知受付は同じDBで直列化し、現在ONの世代だけに受付印を保存します。

将来の画面／HTTP経路では、現在Cookieの本人一致、Origin／CSRF、no-store、現在状態の表示と処理中／結果不明の操作ID回復を別途適用する必要があります。このCore APIだけで画面側の保護が完成したとは扱いません。

## 検証

`dotnet run --project tests/Sem.ManualNotificationPushActivationChecks -c Release` は合成SQLiteで42項目を検証します。旧スキーマ／ボックス保持、既定OFF、全体／担当権限、確認／形式／版、同秒受付境界、同一／無変更／OFF／再ON、再取得時の現認証・本人、監査故障ロールバック、同一／別操作の同時要求、未コミット有効化に受付が待機しコミット後の世代を見ること、上限、配信非変更、監査件数、整合性／外部キー、取消を含みます。一部の直列化試験は合成DBを直接占有するもので、運用での有効化手順ではありません。

残りは運用画面／HTTP制御、上限付き走査／送信・応答分類、送信直前スナップショットと残リース／期限内のタイムアウト／TTL、紐付け保護付き失効処理、Service Worker／実機受入です。ボックス既読／端末到達の保証や外部I/O競合の完全解消は主張しません。
