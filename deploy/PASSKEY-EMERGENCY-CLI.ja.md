# オフラインの最終管理者緊急復旧CLI

これはホスト限定の入口であり、HTTPルート・初期管理者作成・認証迂回ではありません。[PASSKEY-EMERGENCY-RECOVERY.ja.md](PASSKEY-EMERGENCY-RECOVERY.ja.md) の専用HostEmergency処理を使い、アプリ管理者を偽装しません。以下は実行手順であり、実アカウントのリセットやSMTP配信の実施報告ではありません。

## 認可と前提

Linux限定です。root管理の固定ファイル `/etc/sem/emergency-recovery.json` に次の1項目だけを設定します。

```json
{"allowedEffectiveUid":1654}
```

1654は例であり、実際に許可するホスト操作者1名の実効UIDを指定してください。ファイルと各親ディレクトリはroot所有・シンボリックリンクでない実体とし、group/otherによる書込を禁止します。設定は4096バイト以内の通常ファイルです。CLIは開いたファイルと親のLinux statx所有者・モードを確認します。設定パスを変えるCLI引数や環境変数、任意の操作者名を渡す `--operator-id` はありません。欠落・UID不一致・非対応OS・検証不能時は拒否します。コンテナではroot管理の設定を読取専用マウントし、ホスト／コンテナのUID対応を別途確認してください。イメージの非rootユーザーを自動的に許可するものではありません。

対象ストレージを使用する全アプリ・ワーカーを停止します。現行WebとCLIは共通の `sem.runtime.lock` を排他的に保持します。終了後もinodeは残します。使用中のロックを無視するためにファイルを削除しないでください。旧版や任意のSQLiteクライアントは協調ロックに従わない可能性があるため、停止確認が必要です。バックアップ中はSQLite即時トランザクションでも他の書込を阻止します。オンライン保守・強制解除機能はありません。

絶対パスの既存 `Sem:DataDirectory` に `sem.db` と既存 `keys/` が必要です。DBは現行migration履歴・スキーマと完全一致し、未移行モデル変更がなく、整合性・FK検査成功、非WALの清浄なjournal状態でなければなりません。このCLIはDB作成・migration適用・WAL checkpoint・journal変更・HTTP／ワーカー起動を行いません。空でないWAL/SHM/journalは拒否します。必要なオフライン保守は別途承認して実施し、検査を通すためにsidecarを削除しないでください。ストレージ・鍵・バックアップ経路のシンボリックリンクは拒否します。

構成はアセンブリ配下の `appsettings.json` と環境変数（`Sem__DataDirectory`・`Sem__PublicUrl`・`Smtp__Host`・`Smtp__From` 等）から読みます。停止したアプリと同じ対象・設定にしてください。PublicUrlはHTTPS originです。SMTP設定は必要ですが、利用可能性や実配信の検証ではありません。Data Protectionは既存の `SEM.ExternalTest` 鍵リングを使い、自動鍵生成を無効化しています。鍵が使えない場合は代替鍵を黙って生成せず失敗します。

## 二段階処理

1. 対象とDBハッシュを検査します。DB接続は読取専用です。協調ロックファイルだけは作成／オープンし得ます。対象は唯一の有効・メール確認済み全体管理者、またはこのHostEmergencyによる無効化と結び付く再開対象に限定します。無関係な無効アカウントは対象にしません。別宛先の指定はできません。
2. 検査時ハッシュ・対象IDの明示確認付きで準備を適用します。サービスが操作／保護メールを書き込む前に、稼働ストレージ外の新規ディレクトリへDBと全Data Protection鍵ファイルをコピーし、flush・各SHA-256照合・元DB／鍵の再確認・秘密権限のmanifest保存を行います。既存バックアップは上書きしません。バックアップIDはmanifestの順序付き `{path,sha256}` 配列のSHA-256で、操作・監査へ渡します。保存前stampもサービスで再照合します。失敗時の部分バックアップは保持しますが、検証済みとは扱いません。
3. 成功結果は `mail-prepared-no-reset` と操作ID・期限・マスク宛先・バックアップIDです。**CLIは既存キー削除・アカウント無効化・stamp更新・SMTP送信をまだ行っていません。** 速やかにアプリを再開して保護メールを配信します。初回15分期限は待機やワーカー再試行で延長しません。メールを受信・確認できなければ、初回アカウントは変更されません。既に復旧のため無効なアカウントの再開は、その無効状態を保持します。
4. 保存済み確認済みメールの一回確認が成功した時点で初めて、現行適格性・メール・stampを再確認し、キー失効・無効化と短期登録grantを原子的に確定します。Native Identityで期限内に新パスキーを登録し、完了後も通常のログインCookieは発行しません。新キーで通常ログインしてください。永続的な送信／失敗制限・再開条件はサービス文書を参照します。

例（プレースホルダーであり、この文書作成時に実行していません）：

```sh
# アプリ停止、構成が目的の既存ストレージを示していることを確認
dotnet /app/Sem.Web.dll --passkey-emergency-recovery \
  --target-user-id '<正確な利用者ID>' --reason '管理者パスキーを全て紛失'

# 検査結果DatabaseSha256、同一対象、未作成のバックアップ先を指定
dotnet /app/Sem.Web.dll --passkey-emergency-recovery \
  --target-user-id '<正確な利用者ID>' --reason '管理者パスキーを全て紛失' \
  --apply --confirm-target '<正確な利用者ID>' \
  --expected-sha256 '<検査結果の64桁hex>' \
  --backup-directory '/secure-backups/sem-emergency-unique'
```

引数は大小文字を区別し、未知・重複を拒否します。対象は非空白・制御文字なし1〜128文字、理由はtrim後3〜500文字・制御文字なしです。メール・bearer・grant・資格情報の指定引数はありません。検査成功は実アカウントへの実行承認ではなく、実施時は操作者側のインシデント承認に従います。

## バックアップ・監査・ロールバック制約

バックアップディレクトリは排他的に0700、ファイルは0600で新規作成します。DBとData Protection鍵は機密であり、一緒にアクセス制限して保管します。manifestは相対パスとハッシュで、鍵内容・メール・トークンは記録しません。成功結果とmanifestを証跡として保存してください。エラー出力はSQL・秘密値・宛先等を省略します。監査はOS操作者とアプリ管理者を区別し、対象・理由・UTC時刻・復旧元・バックアップdigestを保持します。

準備はDBトランザクションですが、DBとSMTPは分散トランザクションではありません。初回のメール所有確認前にリセットしない設計であり、SMTP利用可能性・実配信を保証しません。メール確認／登録後は**古いDBを自動復元しないでください**。古いキー・Cookie・消費済みcapabilityを復活させるおそれがあります。検証済みバックアップとインシデント記録を保持し、安全対策を含む明示的なロールバック判断を行います。CLIもワーカーもバックアップの削除・置換・自動復元は行いません。

## 受入境界

合成試験はpolicy解析・ロック・バックアップ・前提条件・サービス状態遷移を対象とします。実ホストのmount／UID、操作者本人性、SMTP受信、物理端末WebAuthn、本番復旧の受入証明ではありません。運用導入時は使い捨てアカウントで設定mount・停止対象DB／鍵・バックアップ権限・メール受信・新キー通常ログインを別途確認してから手順を有効化してください。

### 親ディレクトリの保護と結果不明時

稼働ストレージ・鍵ディレクトリ・バックアップ先の直上の親はrootまたは許可実効UIDの所有とし、group/otherの書込を禁止します。全祖先も確認します。`/tmp` のようなroot所有sticky祖先は、操作者所有の子を他ユーザーが差し替えられないため直上の親より上に限り許容します。共有書込可能なディレクトリ直下への保存は拒否します。鍵入力は通常ファイルに限定し、FIFO・socket・device・リンクはhash／copyしません。完了後も保管経路の保護を維持してください。

準備commit後に出力・終了処理が失敗する場合があります。非0終了は操作／メールが存在しない証明ではありません。applyを自動再実行せず、同じ対象を読取専用検査し、`OperationId`・`OperationStatus`・期限・`BackupId`を保全manifestと照合してください。必要なら保護ストレージと監査をオフライン調査します。検査は既存操作を表示しても消費・送信・リセットしません。検査自体も失敗した場合は、証跡を保持してその阻害を解消し、書込結果を推測しないでください。
