# Read-only participant roster foundation

This stage implements the approved v33 participant-roster requirement: one row per current registered person with display name, performance/spectator type, song and part assignments. It is not the manager-only reception roster. It has no reception completion/cancellation action, reception notes/status, private answers, emails or authentication codes.

Current session and effective automatic/manual event phase are revalidated through the existing current-event gate in a read transaction. The public queries never fetch answers, receipt details, profiles or email columns. Hidden events require current global/event management; visible events can be read by ordinary authenticated event viewers. Historical answers/receipts do not create current registration. Multiple parts in the same song are retained within one person row.

The response projects only `userId`, `displayName`, `spectator` and `parts` for people. `GET /api/core/participant-roster?id=...` is no-store/read-only, POST is rejected and continuation is bounded. People are ordered by stable ordinal user identifier, 100 per page; continuation is the last returned identifier, not a cached permission. Concurrent registration changes can change later pages; refresh restarts from current data. The UI labels bounded current totals, provides next/back/refresh, text-encodes values and links to the existing public profile route. No migration is added.

`event-tabs-state.mjs` is a separate pure selection helper, not a completed event tab host. It persists only a tab identifier in a per-user/per-event sessionStorage key. Availability comes from the future server host; invalid, unavailable or another user's selection falls back to event. ArrowLeft/Right/Home/End handling is implemented and tested. No event data, permissions, authentication or browser login snapshot is persisted. Pending mutations/drafts and actual tab panels still require host integration and validation.

Dedicated service tests use 105 synthetic registrants to verify full bounded enumeration; existing regressions remain. Browser checks use actual available authenticated fixtures; they do not claim >100-row real-Blazor pagination unless the fixture actually provides continuation. UI/native/Docker acceptance remains pending until explicitly recorded. No DXP/data/.env/keys, deployment, distribution or merge changes.
