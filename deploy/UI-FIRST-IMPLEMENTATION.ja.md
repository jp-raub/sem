# 採用済みUI優先の実装順と差分台帳

## 基準・完了の意味

- 開始版: main `5aad7c5bff68b605cc82facb7722bc3366121afa`。
- 採用モック: `9cf8b031258fa1c9afe9668f54e61f002c4bce17/mock` と Notion「現行UI仕様・差分台帳（UI MOCK v33）」。モックの上書きスクリプトを含む最終状態を基準とする。古い実装状況欄は現行コードの証拠にはしない。
- 順序: **採用済みの全UI → 残機能 → 利用済み端末のメール入力なしパスキー認証**。UIが必要とする最小限の接続は同じ変更で行う。独立したDB切替・日次バックアップ等は削除せず後続とする。
- この文書は全画面のピクセル一致や全状態の検証完了を宣言しない。以下は現行コンポーネントの静的棚卸しと既存の受入記録から作った一次対応表。各領域の未照合状態は、実装を進める際に固定候補の実描画で確認する。
- 表示、導線、編集／確認モーダル、入力保持、保存・取消、並べ替え、権限差、空／読込／失敗、狭幅／明暗を分けて判定する。仮データや無効なボタンで実装済みに見せない。

## 今回の通知入口の契約

`/notifications` に「このブラウザーの通知設定」と「イベント別の開始通知」を置く。

- イベント一覧は `Core.ReadAsync` の既存認可を通す。専用の公開一覧APIは追加せず、画面にはIDとタイトルだけを描画する。このサービス呼出しがイベント専用の狭いDTOであるとは主張しない。
- 選択時に既存の本人用 `ReadPartStartPreferencesAsync` を読み、既存の保存・イベント版／設定版照合を使う。管理者が他者のONを閲覧・編集するUIにはしない。
- 読み取り／保存中は対象切替と一覧更新を止める。対象キーで子コンポーネントを分け、破棄／遅延応答の世代を照合する。同一対象の親再描画では再初期化しない。
- 競合は最新状態を再取得し、保存を自動で再送しない。権限喪失や結果不明は古いスイッチを消し、手動の一覧再取得で対象を選び直せる。
- ブラウザーのPush処理・許可要求・実送信は変更しない。個人ONは端末許可とは別で、ON以前の開始は遡及しない。
- DB/migration/API形式/配信方式の変更なし。公開候補の一式バックアップ・復元・利用可能性確認、必須CI、公開後の版＋readiness照合を残す。

## 確認負担を減らす進め方

通常のUI判断は採用済みモックを正解として進める。ユーザーの最新指示により、全UIの実装が揃うまで通常の個別承認依頼は起票しない。再現可能な過去の受入は合成データの自動回帰で維持し、仕様上の新しい判断が必要な場合だけ確認する。全UI完了・公開反映・人の受入を別々に記録する。CI改善は本筋ではなく低優先度とし、実装を妨げる不合理な遅延・障害に必要な範囲で対処する。画像10MiBの個別保留とSafari同一ログイン再試験不要は継続する。

## サービス管理の専用画面

共通メニューから `/service` を開き、閲覧時のアカウント一覧・閲覧専用プロフィール・対象を明示選択する認証復旧入口を利用する。既存の業務基盤URLは互換経路として維持する。保存単位と権限の境界、採用v17／v31との対応は [サービス管理UI](SERVICE-MANAGEMENT-UI.ja.md) を参照。全採用UIの完了宣言や個別の承認依頼は行わない。

## コメントの明示キャンセル

コメント専用モーダルには、採用v10の未送信入力を破棄する「キャンセル」を実装する。既存の入力保持付き閉じる／Escapeとは表示と処理を分け、選択中の参加枠・設問回答、通信中・結果不明の操作IDや本文を消さない。現行mainの参加入力ラベルは既に正しい日本語であり、以前の置換文字記録だけを理由に変更しない。
