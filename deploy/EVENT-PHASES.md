# Event phases — preserved data, schedules and manual override

English source of truth. Stacked on the verified core foundation, not an image delivery or DXP deployment.

## Implemented

- `Phases` contains event-local Hidden/View defaults and Custom phases. New events start with Hidden active and automatic evaluation enabled, unless View was explicitly selected. Defaults are not editable/deletable. A unique partial index permits at most one active row; transactions and service validation maintain exactly one.
- `20261012180718_AddEventPhases` creates the phase table and adds `SessionEvents.ManualPhaseOverride`. Each existing formal event receives two defaults, retains its existing Hidden/View selection, version and managers, and starts in manual mode. Migration never retroactively publishes an old hidden event because its start time has passed. Existing accounts/passkeys/invitations/profiles/notification data and earlier migrations are retained. The initial foundation's `PhaseKind` remains a Hidden/View compatibility visibility cache, not the authoritative actual phase kind.
- `/events/{id}/phases` is InteractiveServer management: read-only defaults, custom-name editing panel, add/edit/remove draft, radio selection, automatic/manual mode, final atomic save and cancel. Maximum is a **registered-song count**, -1 unlimited, 0 no picks; enforcement on real song signup is not implemented yet. Names are required and bounded to 100 characters. Time input is explicitly Japan-local; stored times are canonical UTC. API rejects timezone-free date strings, including nested case-insensitive property names.
- A saved manual selection remains active despite its schedule or event start, until the manager saves automatic mode. Automatic selection uses the real server clock: eligible Custom has activation <= now and no end or end > now; latest activation wins, ties use saved list order. Otherwise View at/after event start, Hidden before it. Missing activation means manual-only. End must be later than start when both are present. No fake browser-supplied evaluation time is exposed.
- An actual background worker evaluates automatic events every 15 seconds and on startup. It changes rows, visibility cache, version and a system audit action atomically, and repeated evaluation of the same winner is a no-op. This is not a guarantee of millisecond switching. Writes and worker evaluation serialize via SQLite transactions; stale manager/event-overview drafts are rejected.
- Current enabled/confirmed identity, security stamp, session revocation and actual global/event assignment are checked on every management operation. Viewing Custom only grants event viewing, never global or management permissions. The phase plan is management-only; the public workspace exposes just the active phase summary.
- Removing an inactive custom phase creates a tombstone rather than erasing its identity. The selected active draft cannot be deleted; select another before removing it. An explicitly selected replacement and removal can commit together. Defaults/deleted IDs/foreign-event IDs cannot be forged or resurrected. There is no actual song/participation model in this unit, so preserving future registration references remains a subsequent implementation concern; this unit deliberately does not delete phase history.

## Verification and scope limits

`tests/Sem.PhaseChecks` covers foundation-to-phase migration, defaults, role isolation, unlimited/invalid inputs, time boundaries, overlap/ties, manual override/resume, concurrent/stale drafts, tombstones, forged identifiers, revoked sessions, compatibility overview update, restart and DB uniqueness. Existing core/storage/native-proof/reset regressions remain enabled.

The dedicated CI builds fixed original legacy, fixed foundation `c951ffb`, and candidate images. HTTPS/native virtual-authenticator acceptance runs legacy -> foundation with the existing core UI tests, then migrates populated formal events -> phase candidate; it exercises real Blazor editing/cancel/save, the real scheduled worker, restart and native key re-login. All use synthetic SMTP/accounts/keys and copied data, not DXP.

Not implemented here: event-specific part preset copies, event/profile questions, song slots/signup/answers/capacity, phase-limit enforcement on registrations, complete v33 layout/keyboard-modal polish, live broadcasting, business notification rules, production auth recovery, PostgreSQL and operational backups. Phase changes do not automatically email or Push anyone. No `.env`, SMTP/VAPID/DP key, RP, proxy, original volume, image delivery or PR merge is performed. Deployment acceptance remains a separate copied-volume operation.

**Continuation:** after tests are green, event definitions/preset copies and questions can proceed without a new user decision under the existing authorization. New requirements or contradictions must be presented explicitly before implementation. Every checkpoint states whether it is ready to continue or blocked on a specific user confirmation.
