# mock起点の検証範囲

採用mockを正解にすることと、旧UI向けfull一式を戻すことは別とする。

## 維持する基準

- 固定mock171資産と全JS構文を検査する。最終ラッパー適用後の72表示・22タブ・代表4モーダルを画面基準として使う。
- 稼働版・nonce・readiness・公開候補・updaterの保護検査は維持する。モックの成功を実認証・保存・QR・Pushの成功に読み替えない。
- 古いモック同梱qa結果は履歴であり、今回の実行結果とは扱わない。旧UI専用fullを全変更で再実行しない。

## 今回見直したもの

保存基盤は公開ホストへ未接続のため、**mock資産／画面基準／対象スクリプト／資料だけの変更**で、同じ保存基盤build・22検査を機械的に反復しない。`test-scope.py` がGit差分から実行範囲を判定する。

ただし次は保存基盤検証を実行する：モデル・migration・抽出ツール・保存検証・Webホスト／project・認証等の変更、CI自身の変更、未知のファイル、手動実行、差分の取得失敗、空の差分、履歴不足。既知のUI／資料だけを対象外とする許可リスト方式で、認証・DBの既知パスだけを実行する方式にはしない。

PRはbase SHA、pushはbefore SHAとの差分を使う。checkoutは2世代取得し、必要な履歴がなければ全検査へ戻る。判定の7テストは毎回実行する。必須job名、固定mockと版API、ブラウザー回帰は変更しない。

この調整は無関係な検証の反復を減らすもので、CI全体の時間短縮を測定前に保証しない。最終UIの配置・狭幅／明暗・フォーカス等は機能接続単位で確認し、見出し一致だけで全UI完了とはしない。

## READMEの扱い

ユーザー指示によりルートのREADME.mdをいったん削除する。固定mockの同梱README資産は171資産の由来・バイト一致を維持するため変更しない。要件・方針・実行状態はNotionの各正本、対象commitの実装・検証詳細はdocsとPRで追跡する。

## ブラウザーCIの環境準備と障害切り分け

`playwright install --with-deps` による毎回のapt取得は行わない。実際にUbuntuミラーのパッケージ取得中にジョブ全体の8分上限へ達したため、ブラウザーとOS依存が同梱された公式Playwrightイメージを版・digest固定で使う。npmのPlaywrightも同じ1.56.1へ固定する。イメージにはnpmパッケージ自体は含まれないため、それだけを別途導入し、同梱Chromiumの存在を確認する。

準備・アプリbuild・起動・版表示・画面基準を別stepへ分割し、それぞれの上限と失敗箇所をActions上で確認できるようにする。ジョブ全体の8分上限、必須job名、11版表示検査と322画面検査、公開候補の安全条件は維持する。失敗時は隔離した合成ホストのログだけを3日間保存し、ホストを終了する。公開先secretはこのjobへ渡さない。

ネットワーク障害を完全になくす措置ではない（イメージ・npm・.NETの取得は残る）。準備の成功をテスト成功と扱わず、テスト失敗は引き続き公開を止める。CI変更自体は保存基盤を含む集中検証の対象となる。公式説明: https://playwright.dev/docs/docker
