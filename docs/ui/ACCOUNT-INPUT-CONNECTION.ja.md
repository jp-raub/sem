# 本人アカウントの入力・確認UIと未接続の認証変更

## 実装範囲

要件正本はNotion「要件・整合性・テスト観点」。固定mockのaccount hub・旧キー入口・メール変更入口・追加フロー最初の段階・削除確認のDOMと共通CSSを採用する。固定171資産・旧モデル／migrationは変更しない。

- メール変更：新アドレスを入力・検証でき、再認証前の確認を開く。254文字を上限とし、既存メールや実アドレスを初期入力しない。空・不正形式で確認へ進まない。
- パスキー追加：現在本人を再照合して、採用3段階の最初「既存パスキー再認証」を表示する。戻ると本人のアカウント管理へ戻る。
- パスキー削除：複数キー時だけ確認入口を有効にする。現在の本人・キー一覧を開く直前に再取得し、表示名／日時の一覧が変わっていた場合は古い行を流用しない。最後のキーは確認入口も無効とする。

**実再認証・メール送信／確認・キー追加／削除・メール変更保存は未接続**。確定ボタンは無効、formのsubmitを直接発火しても閉鎖・成功・「確認済み」への遷移をしない。デモの段階送り・模擬認証・模擬メール確認は移植しない。復旧・新規登録・追加の後続段階が動くようにも見せない。

キーのCredential ID等を新たに取得しない。行番号と名称／日時の照合は、この未接続確認UIだけのローカル前提であり、将来の削除APIの対象指定・競合保護・本人確認の代用にはしない。

## 入力と取消

メール下書きは本人×現在ページのJSメモリ内だけ。定期読取でも入力とフォーカスを保持する。再認証前の確認を閉じただけなら、下のメール入力は残る。ページ移動・再読込・ログアウト・失効・取得失敗では破棄し、localStorage／sessionStorageにメールを保存しない。

確認は採用native dialogを使い、キャンセル・×・Escape・背景で閉じる。閉鎖後は本文を消し起点へフォーカスを戻す。モーダル内をTab／Shift+Tabで循環し、未接続確定へは進まない。閉じた後に遅れた参照応答を適用しない。

現在本人の参照が401、失敗、別人、秘密列を含む未知DTOの場合は古い本人情報・下書き・追加表示を消す。正常なキー0件は取得失敗と区別する。参照APIと既存180読取／分・no-storeは維持する。

## 検証

- 合成HTTPSの現在本人メール／標準キーを使用。削除の複数キー表示は合成DTOで比較し、実キーが複数存在する証拠にしない。
- 固定mockと4幅×明暗でメール入力・確認、追加フロー骨格を比較する。下書きの定期読取保持、移動／再読込での破棄、閉鎖4方式、フォーカス、最後のキー、対象変化、遅延、失敗／401を検査する。
- POST等0、認証器get／create要求0、参照前後の保存済みDTO不変を確認する。検査の認証器計測は文書再読込後も継続し、検査終了時にフックを解除する。
- 初回の集中検査は、再読込で検査用windowカウンターが消えたため最後の計測assertで失敗した。文書ごとのフックとNode側の累積計測へ修正し、新規合成DBから再実行する。実際の認証器要求が発生したと断定せず、失敗を成功へ流用しない。

公開配置は既定demoのまま、実volume・DB・鍵・秘密設定へ触れない。認証変更機能や全UIの完成、ユーザー実機受入とは分ける。
