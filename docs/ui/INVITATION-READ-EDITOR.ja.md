# 招待管理：本人の参照・発行リクエスト入力

## 実装した範囲

要件正本F03・U05〜U07・D03〜D04に対応する分割実装。固定mockの本人向け招待管理の見出し、2つのpanel、依頼カード／状態badge、発行記録カード、中央リクエスト入力を製品用アダプターへ接続する。固定171資産は変更しない。

`GET /api/ui/invitations` と `/api/ui/invitations/page/{page}` は、現認証の本人に所属する依頼・発行記録だけを返す。全体管理者であってもこのAPIは他人の記録を返さない。判断・全体台帳・直接発行・緊急失効の管理者画面は後続で、この本人向け参照の表示を管理者UI完成としない。

## 参照の安全境界

- 同一SQLite読取snapshotでセッションの有効性、本人、現在の役割、本人の記録と判断者表示名を参照する。ユーザーをqueryで指定できず、GET以外・本文・不正ページを拒否する。既存の180読取/分を維持する。
- SQLでUserId／OwnerIdを本人へ限定する。発行者が本人というだけでは他人宛リンクを返さない。
- TokenHash、ProtectedToken、発行目的、メール、認証情報をSQL射影にもDTOにも含めない。登録用リンクは復号・生成・推測しない。発行済みレコードがあることと、登録用URLを利用可能にしたことを区別する。
- 依頼と発行記録を各100件、作成日時降順・ID降順で取得し、それぞれの続きの有無を表示する。ページは両区画共通で、一方が空でも他方の続きへ進める。
- 0／未記録の日時・判断者は不明とし、発行期限や人数上限を無制限へ勝手に変換しない。無効・期限切れ・上限到達・有効・旧条件不明を区別する。不正な保存値は422とし、0件へ変換しない。
- no-store。理由・判断コメント・名前はHTMLとして扱わない。失敗・不正DTO・別本人・401・画面移動・遅延応答で以前の私的表示や入力を残さない。

## 入力と取消

入力を開く直前に本人の現認証と参照を再確認する。理由は必須・500文字、人数1〜5／日数1〜7、既定は各1。採用中央dialog、短い必須ラベルと日数の補足ヘルプ、フォーカス循環・起点復帰を使用する。日数の補足は固定mockに合わせた外部日本語JSONで、実行コードや利用者の入力を説明として使わない。

送信は未接続として無効化する。入力はdialog内のメモリだけで、キャンセル・×・Escape・背景操作は破棄する。再表示で復元しない。保存・通知・リンク発行・利用人数の消費・監査記録・成功トーストは発生しない。承認／拒否・直接発行・失効・登録完了による人数消費は、現認可・操作ID・競合・通知と一緒に後続接続する。

## 検証方針

合成DB・鍵・標準仮想パスキーで実製品HTTPSを使い、他人の記録／秘密値除外、各状態、100件超、日時不明、入力制約、取消、再試行、別本人・不正DTO・401と遅延を検査する。320／390／768／1440px×明暗で採用最終mockと主要スタイルを比較する。参照と入力操作のPOST等0・記録不変を確認する。CI既定は既存回帰を省略せず全接続検査へ追加する。公開既定demo・実volume未接触・README削除は維持する。

合成fixtureのTokenHash重複による起動失敗を検出した過程で、既存harnessがsignal終了後のcleanupを未完了promiseにして無出力exit0となる問題も再現した。ready／stopでsignal終了を扱い、同じ失敗fixtureが固定エラー・exit1になることを確認してから、fixtureの合成ハッシュを一意に直す。無出力の試行は成功検査数に含めない。失敗試行も最終検証記録へ残す。

signal終了済みの子プロセスに対するstop完了・ready拒否もharnessの毎回の実行に組み込む。外部の製品ホストやCI判定は使わず、短命なNode子プロセスだけで失敗経路を検査する。JSONをProductUIへ追加する際のSDK既定Contentとの重複も修正し、以降のローカル実行はpublish成功を前提にする。途中のpublish失敗／古い配置を使った試行は最終固定候補の成功へ流用しない。
